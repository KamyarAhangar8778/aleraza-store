# نقشه راه و حافظهٔ پروژه آلِرضا استور

> هدف این سند: انتقال زمینهٔ تصمیم‌ها و گفتگو به چت‌های بعدی. هر AI Agent باید این فایل را همراه با قوانین پروژه و معماری فعلی بخواند تا کار از همین نقطه ادامه پیدا کند.
>
> آخرین به‌روزرسانی: 2026-10-17

## 1. خلاصهٔ اجرایی

پروژهٔ **Aleraza Store** یک فروشگاه آنلاین فارسی و RTL است. مخزن اصلی:
- https://github.com/KamyarAhangar8778/aleraza-store

قرار است UI/UX و قابلیت‌های فروشگاه به‌صورت تدریجی توسعه پیدا کنند، اما پیش از هر تغییر باید معماری اجرایی با محدودیت واقعی هاست سازگار شود. کاربر می‌خواهد ابتدا **عملکرد اصلی فروشگاه** پایدار و قابل استفاده شود و پس از آن روی **SEO صفحات محصول** تمرکز کنیم.

محدودیت بنیادی هاست: فقط **PHP و WordPress** در دسترس است و امکان اجرای Node.js وجود ندارد. بنابراین فرانت‌اند باید خروجی استاتیک قابل میزبانی روی این هاست تولید کند و قابلیت‌های بک‌اند باید از طریق PHP/WordPress API فراهم شوند.

## 2. تصمیم‌های تأییدشده توسط کاربر

این موارد را به‌عنوان قیود قطعی در نظر بگیر، مگر اینکه کاربر بعداً آن‌ها را تغییر دهد:

1. **هاست فقط PHP و WordPress دارد؛ Node.js قابل اجرا نیست.**
2. **خروجی فرانت‌اند باید استاتیک باشد.** نباید راه‌حل نهایی به Next.js server runtime وابسته باشد.
3. **Firebase باید حذف شود.** دسترسی به Firebase برای کاربران داخل ایران محدود یا غیرقابل اتکاست و نمی‌تواند وابستگی حیاتی فروشگاه باقی بماند.
4. **مدیریت محصولات:** پنل مدیریت اختصاصی فروشگاه با بک‌اند PHP و API.
5. **مدیریت کاربران:** سیستم اختصاصی ثبت‌نام و ورود، بدون Firebase.
6. **اولویت توسعه:** ابتدا عملکرد فروشگاه، سپس SEO صفحات محصول.
7. **دامنهٔ فروشگاه:** فروشگاه روی دامنهٔ اصلی قرار بگیرد. ترجیح این است که بلاگ روی مسیر `/blog/` باشد؛ اگر استقرار این ساختار دشوار یا ناسازگار بود، `blog.example.com` گزینهٔ جایگزین است.
8. کاربر می‌خواهد توسعه با تغییرات کوچک و قابل بررسی انجام شود، نه بازنویسی یک‌بارهٔ پروژه.
9. مخزن از طریق GitHub integration قابل دسترسی است؛ تغییرات باید در همان repository ثبت شوند. پیش از تغییرات کد، فرضیات و ابهام‌های مهم را روشن کن.

## 3. قوانین الزامی مخزن

در ابتدای هر چت جدید مرتبط با مخزن، این فایل‌ها را از branch پیش‌فرض بخوان و از آخرین نسخه‌شان پیروی کن:

1. [AGENTS.md](../AGENTS.md)
2. [SKILLS-GUIDE.md](../.agents/skills/SKILLS-GUIDE.md)
3. [ARCHITECTURE.md](../ARCHITECTURE.md)

قوانین برجستهٔ `AGENTS.md`:
- قبل از کدنویسی هدف، معیار پذیرش و فرضیات را مشخص کن؛ اگر ابهام مهمی وجود دارد، سؤال بپرس.
- اصل Simplicity First و تغییرات جراحی (surgical changes) را رعایت کن.
- فایل را برای تغییر چند خط از نو بازنویسی نکن و refactor نامرتبط انجام نده.
- مسئولیت هر فایل روشن و ماژولار باشد؛ معمولاً فایل‌های کد را بی‌دلیل بزرگ نکن (راهنمای پروژه حدود 200–300 خط را هدف می‌گیرد و تا حدود 400 خط را با توجه به خوانایی قابل قبول می‌داند).
- Skill مرتبط را فقط اگر واقعاً موجود و قابل خواندن/اجراست استفاده کن؛ وجود Skill در فهرست راهنما به‌تنهایی به معنی دسترسی به فایل آن نیست.
- پس از هر تغییر، lint، format، syntax، تست مرتبط و build را تا حد امکان اجرا کن و خروجی واقعی را گزارش بده. چیزی را که اجرا نشده، تأییدشده اعلام نکن.
- تغییرات را در صورت امکان با چند ابزار/خواندن موازی جلو ببر، اما عملیات وابسته را موازی نکن.
- معماری فعلی و فایل‌های مرتبط را پیش از تغییر بررسی کن.

نکتهٔ مهم: `ARCHITECTURE.md` فعلی هنوز معماری قدیمی Firebase را شرح می‌دهد. تا زمانی که مهاجرت واقعاً انجام نشده، آن را توصیف وضعیت فعلی بدان، نه معماری هدف.

## 4. وضعیت فعلی کدبیس که تاکنون بررسی شده

تکنولوژی‌ها و فایل‌های مهم:
- Next.js 15 App Router، TypeScript، React 19 و Tailwind CSS.
- `app/page.tsx`: صفحهٔ اصلی فروشگاه.
- `app/layout.tsx`: لایهٔ اصلی.
- `app/admin/page.tsx`: صفحهٔ پنل مدیریت.
- `components/StoreProvider.tsx`: اتصال state مرکزی فروشگاه.
- `hooks/useStoreProducts.ts`: محصولات/دسته‌ها و عملیات CRUD متصل به Firestore.
- `hooks/useStoreAuth.ts`: احراز هویت وابسته به Firebase؛ بخشی از وضعیت نشست نیز در localStorage نگهداری می‌شود و باید در طراحی جدید بازبینی شود.
- `hooks/useStoreCart.ts`: سبد خرید و localStorage؛ احتمالاً بخش محلی سبد می‌تواند باقی بماند، اما قیمت/موجودی نهایی باید در سرور اعتبارسنجی شود.
- `lib/firebase.ts`: راه‌اندازی Firebase.
- `firestore.rules`: قوانین دسترسی Firebase.
- `ARCHITECTURE.md`: سند معماری فعلی، مبتنی بر Firebase.

### نکتهٔ مهم دربارهٔ خروجی استاتیک

در `next.config.ts`، تنظیم `output` در حال حاضر فقط وقتی `GITHUB_PAGES=true` باشد `export` است؛ در حالت عادی `standalone` انتخاب می‌شود. پس پروژه هنوز به‌طور پیش‌فرض برای هاست PHP-only خروجی استاتیک نمی‌سازد.

قبل از تغییر تنظیمات، باید routeها و وابستگی‌ها ممیزی شوند: dynamic routes، API/server features، استفاده از `headers()`/`cookies()`، مسیرهای تولید استاتیک، image handling، و هر قابلیت دیگری که با static export ناسازگار باشد. صرف تغییر `output: 'export'` بدون این ممیزی کافی نیست.

فایل `package.json` شامل اسکریپت‌های `dev`، `build`، `start`، `lint` و `clean` است. وابستگی Firebase هنوز در پروژه وجود دارد.

## 5. معماری هدف پیشنهادی (هنوز پیاده‌سازی نشده)

این بخش جهت فنی مورد توافق/پیشنهادشده را ثبت می‌کند؛ این معماری هنوز در کد اجرا نشده است.

### Frontend
- حفظ UI فعلی Next.js تا جای ممکن و تولید خروجی استاتیک قابل میزبانی.
- اتصال فرانت‌اند به API مبتنی بر PHP از طریق درخواست‌های HTTP.
- اجتناب از وابستگی runtime به Node.js یا قابلیت‌های server-side خود Next.js.
- حفظ فارسی، RTL و واحد پول تومان.

### Backend و داده
- استفاده از WordPress/PHP و MySQL/MariaDB به‌عنوان زیرساخت قابل میزبانی و منبع حقیقت داده‌ها.
- پیاده‌سازی منطق اختصاصی فروشگاه در یک **افزونهٔ اختصاصی WordPress** (نام پیشنهادی: `aleraza-store-api`) به‌جای قراردادن منطق دامنه در قالب.
- استفاده از WordPress REST API با namespace اختصاصی، مثلاً `/wp-json/aleraza/v1/`.
- WordPress برای بلاگ و محتوای SEO نیز استفاده شود.
- قبل از نهایی‌کردن مدل دیتابیس، ساختار واقعی محصولات، دسته‌بندی‌ها، تصاویر، تنظیمات، کاربران و قابلیت‌های موجود باید بررسی و مستند شود.

### نمونهٔ اولیهٔ قرارداد API (برای بازبینی، نه قرارداد نهایی)
- محصولات: `GET /products`، `GET /products/{id}`
- دسته‌ها: `GET /categories`
- عملیات مدیریت: `POST /admin/products`، `PATCH /admin/products/{id}`، `DELETE /admin/products/{id}`
- احراز هویت: `POST /auth/register`، `POST /auth/login`، `POST /auth/logout`
- حساب کاربر: `GET /me`، `PATCH /me`
- مدیریت کاربران/نقش‌ها: `GET /admin/users`، `PATCH /admin/users/{id}/role`

این endpointها صرفاً طرح اولیه‌اند؛ قبل از پیاده‌سازی باید با قابلیت‌های واقعی، مدل داده و نیازهای فروشگاه تطبیق داده شوند. از ساخت endpointهایی که نیازی به آن‌ها ثابت نشده پرهیز کن.

### امنیت احراز هویت و مدیریت
- اعتبارسنجی دسترسی مدیر باید در سرور PHP انجام شود؛ پنهان‌کردن UI یا نقش ذخیره‌شده در کلاینت کنترل دسترسی محسوب نمی‌شود.
- رمزها با روش امن سمت سرور (مانند `password_hash` و `password_verify`) مدیریت شوند.
- نشست‌ها با cookieهای مناسب و امن (HttpOnly، Secure در HTTPS و SameSite متناسب با flow) مدیریت شوند؛ از ذخیرهٔ token احراز هویت در localStorage پرهیز شود.
- محافظت CSRF، rate limiting، اعتبارسنجی ورودی و کنترل دسترسی سمت سرور در طراحی لحاظ شود.
- قبل از سفارش/پرداخت، سرور باید قیمت، موجودی و اقلام سبد را مجدداً اعتبارسنجی کند؛ مقدارهای ارسالی مرورگر قابل اعتماد نیستند.

### تصاویر و آپلود
- محل نهایی نگهداری تصاویر و نحوهٔ آپلود (احتمالاً WordPress Media Library یا راه‌حل سازگار با هاست) هنوز تعیین نشده و باید پس از بررسی جریان فعلی مدیریت محصول تصمیم‌گیری شود.

## 6. راهبرد مهاجرت

مهاجرت باید مرحله‌ای و قابل بازگشت باشد؛ از حذف فوری Firebase یا نوشتن هم‌زمان در دو منبع داده اجتناب شود.

1. **ممیزی فقط‌خواندنی:** routeها، قابلیت‌های Next.js، وابستگی‌های Firebase، مدل داده، CRUD ادمین، احراز هویت، سبد/سفارش و جریان آپلود را فهرست کن.
2. **تثبیت قرارداد داده و API:** بر اساس نیازهای واقعی فعلی، schema و پاسخ‌های API را مشخص کن.
3. **آماده‌سازی استاتیک:** ناسازگاری‌های static export را با کمترین تغییر لازم رفع و خروجی را build کن.
4. **Backend/API:** افزونهٔ WordPress و endpointهای ضروری را به‌صورت کوچک و مستقل پیاده‌سازی کن.
5. **انتقال خواندن محصولات:** ابتدا دریافت محصولات/دسته‌ها از API جدید و حالت loading/error را آزمایش کن.
6. **انتقال CRUD مدیریت:** افزودن/ویرایش/حذف محصول را روی دیتابیس WordPress بررسی کن.
7. **انتقال کاربران و احراز هویت:** پس از تعیین نیازهای ورود/ثبت‌نام، flow امن PHP را پیاده کن.
8. **مهاجرت و تطبیق داده:** پیش از سوئیچ، backup بگیر، تعداد و محتوای رکوردها را مقایسه کن و روش بازگشت داشته باش.
9. **حذف Firebase:** فقط پس از تأیید اینکه قابلیت‌های مربوطه به‌طور کامل به سیستم جدید منتقل شده‌اند.
10. **استقرار و مسیرها:** مسیریابی فایل‌های استاتیک، `/blog/`، `/wp-admin/` و `/wp-json/` را روی محیط هدف بررسی کن.
11. **SEO محصول:** بعد از پایداری عملکرد، سراغ URLهای محصول، metadata، structured data، sitemap، canonical، محتوای قابل crawl و سایر نیازهای SEO برو.

ترتیب دقیق ممکن است با یافته‌های ممیزی اصلاح شود. از dual-write به‌عنوان راه‌حل پیش‌فرض استفاده نکن؛ منبع داده و ترتیب cutover باید شفاف باشد.

## 7. معیارهای پذیرش مرحلهٔ اول

- فرانت‌اند با فایل‌های استاتیک روی هاست بدون Node.js اجرا شود.
- قطع یا محدودیت Firebase هیچ قابلیت حیاتی فروشگاه را مختل نکند و پس از مهاجرت وابستگی runtime آن حذف شده باشد.
- افزودن، ویرایش و حذف محصول از پنل مدیریت در دیتابیس WordPress/PHP ثبت شود.
- ثبت‌نام/ورود طبق flow نهایی بدون Firebase کار کند.
- کنترل نقش مدیر سمت سرور انجام شود.
- قیمت و موجودی قبل از هر عملیات حساس سمت سرور اعتبارسنجی شود.
- مسیرهای API، بلاگ و فایل‌های استاتیک در هاست با هم تداخل نداشته باشند.
- lint، format/syntax، تست‌های مرتبط و build بررسی شوند؛ موارد غیرقابل اجرا صریحاً گزارش شوند.
- پس از تغییر معماری، مستندات معماری با وضعیت واقعی همگام شوند.

## 8. پرسش‌های باز و مواردی که باید بررسی شوند

این‌ها پرسش‌ها و ابهام‌های واقعی باقی‌مانده‌اند؛ همه لازم نیست قبل از ممیزی پاسخ داده شوند. اول با کد موجود و امکانات هاست تا حد ممکن پاسخ‌ها را پیدا کن، سپس فقط سؤال‌های تصمیم‌ساز را از کاربر بپرس.

### استقرار و هاست
- آیا WordPress اکنون نصب شده یا قرار است نصب شود؟
- آیا تنظیمات Apache/.htaccess یا Nginx قابل تغییرند؟ (مهم برای `/blog/` و routing استاتیک.)
- آیا فرانت‌اند و WordPress روی یک document root قرار می‌گیرند؟ مسیر استقرار و URL پایهٔ API چیست؟
- آیا HTTPS روی دامنهٔ اصلی و مسیرهای API فعال است؟
- آیا محدودیت CORS یا سیاست امنیتی هاست باید لحاظ شود؟

### دامنهٔ فروشگاه
- آیا سفارش/checkout، درگاه پرداخت، ارسال، کد تخفیف یا موجودی انبار در نسخهٔ فعلی وجود دارد و باید در فاز اول حفظ شود؟ ابتدا این موارد را از repo استخراج کن.
- ساختار واقعی محصول چیست؟ (SKU، قیمت عادی/تخفیف، قیمت همکاری، حداقل خرید عمده، ویژگی‌های فنی، موجودی، وضعیت انتشار، چند تصویر، دسته‌بندی و اسلاگ.)
- آیا کاربران با شماره تلفن/رمز عبور وارد می‌شوند؟ آیا Google sign-in فعلی باید حذف شود یا جایگزین خاصی مدنظر است؟
- آیا کاربران/محصولات فعلی باید از Firebase export شوند؟ اگر بله، چه دسترسی/فایلی برای داده‌ها در اختیار است؟
- آیا پنل مدیریت فعلی تمام قابلیت‌ها را باید حفظ کند؟ پیش از تصمیم، قابلیت‌های موجود را فهرست کن.
- تصاویر محصولات باید در WordPress Media Library باشند یا سرویس/فضای دیگری در دسترس است؟

### سئو و محتوا
- بلاگ و فروشگاه باید در یک نصب WordPress باشند یا نصب جداگانه‌ای برای بلاگ مدنظر است؟
- برای صفحات محصول، URL نهایی باید از ابتدا مسیر مستقل داشته باشد یا در فاز عملکرد فقط API/داده را آماده کنیم؟ فعلاً اولویت SEO پایین‌تر است، اما تصمیم routing نباید مهاجرت آینده را غیرضروری سخت کند.

### عملیات و نگهداری
- آیا امکان اجرای build محلی/CI و بارگذاری پوشهٔ خروجی استاتیک در روند انتشار فعلی وجود دارد؟
- روش backup دیتابیس WordPress و بازیابی در هاست چیست؟
- چه محیطی برای تست API و احراز هویت قبل از انتشار production داریم؟

## 9. قدم بعدی دقیق

**بدون تغییر کد، یک ممیزی سازگاری static export و وابستگی‌های Firebase انجام بده و نتیجه را به شکل یک گزارش کوتاه و مستند ارائه کن.**

خروجی ممیزی باید شامل موارد زیر باشد:
1. فهرست routeها و موارد ناسازگار با static export.
2. همهٔ محل‌های استفاده از Firebase و قابلیت وابسته به هر کدام.
3. جریان فعلی CRUD محصولات/دسته‌ها/تنظیمات و کاربران.
4. فهرست قابلیت‌های فروشگاهی که باید حفظ شوند.
5. طرح API حداقلی پیشنهادی و مواردی که هنوز برای تصمیم‌گیری نیاز به پاسخ کاربر دارند.
6. پیشنهاد ترتیب مهاجرت با معیارهای verification هر مرحله.

در این مرحله **هنوز مجاز به حذف Firebase، تغییر پیکربندی build یا شروع بازنویسی نیستی**؛ ابتدا گزارش را آماده کن و ابهام‌های مهم را مطرح کن. پس از تأیید جهت کار، پیاده‌سازی را مرحله‌ای آغاز کن.
