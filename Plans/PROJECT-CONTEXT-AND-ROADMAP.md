# نقشه راه و حافظهٔ پروژه آلِرضا استور

> هدف: انتقال زمینهٔ تصمیم‌ها به چت‌های بعدی. این سند را همراه با قوانین پروژه و معماری فعلی بخوان.
> آخرین به‌روزرسانی: 2026-10-17

## 1. خلاصهٔ اجرایی

Aleraza Store یک فروشگاه آنلاین فارسی و RTL است. مخزن: https://github.com/KamyarAhangar8778/aleraza-store

هدف فقط ساخت UI زیبا یا یک سیستم سفارشی شبیه WordPress نیست. **WordPress باید هستهٔ واقعی مدیریت محتوا و تجارت فروشگاه باشد و پروژه باید با اکوسیستم آن همکاری کند.** کاربر مشخصاً می‌خواهد بتواند محصولات را در سرویس‌هایی مثل **ترب (Torob)** ثبت و عرضه کند و از قابلیت‌ها و افزونه‌های جاافتادهٔ WordPress برای SEO، مدیریت محصول و محتوا استفاده کند.

اولویت توسعه: ابتدا عملکرد اصلی فروشگاه پایدار شود؛ سپس SEO صفحات محصول و توزیع محصول در کانال‌هایی مثل ترب با تکیه بر قابلیت‌های واقعی WordPress بهینه شود. تصمیم‌های فنی فاز عملکرد نباید SEO، فید محصول و یکپارچگی‌های آینده را بی‌دلیل سخت کنند.

محدودیت هاست: فقط PHP و WordPress در دسترس است و Node.js قابل اجرا نیست. بنابراین فرانت‌اند فعلی باید خروجی استاتیک قابل میزبانی تولید کند، مگر اینکه پس از بررسی امکانات واقعی هاست راه دیگری صریحاً تأیید شود.

## 2. تصمیم‌های تأییدشده توسط کاربر

1. هاست فقط PHP و WordPress دارد؛ Node.js قابل اجرا نیست.
2. فرانت‌اند باید خروجی استاتیک داشته باشد و به Next.js server runtime وابسته نباشد.
3. Firebase باید حذف شود؛ دسترسی به آن برای کاربران داخل ایران محدود یا غیرقابل اتکاست.
4. **WordPress باید هستهٔ واقعی CMS/Commerce باشد، نه صرفاً یک بک‌اند سفارشی شبیه WordPress.** تا جای ممکن از مدل داده، مدیریت محتوا، REST API، افزونه‌ها و اکوسیستم WordPress استفاده شود؛ قابلیت‌هایی که WordPress/WooCommerce استاندارد فراهم می‌کنند بی‌دلیل بازسازی نشوند.
5. پنل مدیریت اختصاصی فعلی می‌تواند در صورت نیاز باقی بماند، اما باید با هستهٔ داده و API وردپرس یکپارچه باشد. اینکه پنل بومی WordPress/WooCommerce کافی است یا پنل سفارشی باید حفظ شود، پس از ممیزی تصمیم‌گیری شود.
6. برای ثبت‌نام/ورود بدون Firebase نیاز وجود دارد؛ قبل از ساخت سیستم auth جدید، قابلیت‌های بومی WordPress و نیاز UX بررسی شوند. سیستم جداگانه بدون دلیل ساخته نشود.
7. **ثبت و عرضهٔ محصولات در ترب (Torob) یک نیاز مهم محصولی است.** باید بررسی شود آیا integration معتبر WordPress/WooCommerce وجود دارد یا باید feed مطابق مشخصات جاری ترب تولید شود. تا بررسی مستندات فعلی، روش دقیق و الزامات را قطعی فرض نکن.
8. اولویت: ابتدا عملکرد فروشگاه، سپس SEO صفحات محصول؛ با این حال ساختار محصول و URLها از ابتدا تا حد ممکن SEO- و feed-friendly طراحی شوند.
9. فروشگاه روی دامنهٔ اصلی باشد. ترجیحاً بلاگ روی /blog/؛ اگر دشوار یا ناسازگار بود، blog.example.com گزینهٔ جایگزین است.
10. توسعه باید مرحله‌ای، با تغییرات کوچک و قابل بررسی باشد.
11. تغییرات باید در همین repository ثبت شوند. پیش از تغییر کد، فرضیات و ابهام‌های مهم را روشن کن.

## 3. قوانین الزامی مخزن

در ابتدای هر چت جدید مرتبط با مخزن، آخرین نسخهٔ این فایل‌ها را از branch پیش‌فرض بخوان:
1. ../AGENTS.md
2. ../.agents/skills/SKILLS-GUIDE.md
3. ../ARCHITECTURE.md

قوانین برجستهٔ AGENTS.md:
- پیش از کدنویسی هدف، معیار پذیرش و فرضیات را مشخص کن؛ اگر ابهام مهمی وجود دارد، سؤال بپرس.
- Simplicity First و surgical changes؛ فایل را برای تغییر چند خط از نو بازنویسی نکن و refactor نامرتبط انجام نده.
- مسئولیت فایل‌ها روشن و ماژولار باشد؛ فایل کد را بی‌دلیل بزرگ نکن.
- Skill مرتبط را فقط اگر واقعاً موجود و قابل خواندن/اجراست استفاده کن؛ وجود Skill در راهنما به‌تنهایی به معنی دسترسی به آن نیست.
- پس از هر تغییر lint، format، syntax، تست مرتبط و build را تا حد امکان اجرا کن و خروجی واقعی را گزارش بده. چیزی را که اجرا نشده، تأییدشده اعلام نکن.
- معماری فعلی و فایل‌های مرتبط را پیش از تغییر بررسی کن.

ARCHITECTURE.md فعلی هنوز معماری قدیمی Firebase را شرح می‌دهد. تا زمان مهاجرت، آن را توصیف وضعیت فعلی بدان، نه معماری هدف.

## 4. وضعیت فعلی کدبیس که تاکنون بررسی شده

- Next.js 15 App Router، TypeScript، React 19 و Tailwind CSS.
- app/page.tsx: صفحهٔ اصلی فروشگاه.
- app/layout.tsx: لایهٔ اصلی.
- app/admin/page.tsx: پنل مدیریت.
- components/StoreProvider.tsx: state مرکزی فروشگاه.
- hooks/useStoreProducts.ts: محصولات/دسته‌ها و CRUD متصل به Firestore.
- hooks/useStoreAuth.ts: احراز هویت وابسته به Firebase؛ وضعیت نشست در localStorage نیز باید بازبینی شود.
- hooks/useStoreCart.ts: سبد خرید و localStorage؛ می‌تواند محلی باقی بماند، اما قیمت/موجودی نهایی باید سمت سرور اعتبارسنجی شود.
- lib/firebase.ts و firestore.rules: اتصال و قوانین Firebase.
- ARCHITECTURE.md: معماری فعلی مبتنی بر Firebase.

### Static export
در next.config.ts، output فقط وقتی GITHUB_PAGES=true باشد export است؛ در حالت عادی standalone انتخاب می‌شود. پس پروژه هنوز به‌طور پیش‌فرض خروجی استاتیک تولید نمی‌کند. پیش از تغییر تنظیمات، routeها و قابلیت‌های ناسازگار باید ممیزی شوند: dynamic routes، API/server features، headers()/cookies()، تولید مسیرهای استاتیک و تصاویر. صرف تغییر output به export کافی نیست.

package.json شامل dev، build، start و lint است و وابستگی Firebase هنوز وجود دارد.

## 5. معماری هدف پیشنهادی (هنوز پیاده‌سازی نشده)

### اصل معماری
**WordPress باید منبع اصلی داده و هستهٔ واقعی مدیریت فروشگاه/محتوا باشد.** ابتدا قابلیت‌های بومی WordPress و در صورت تناسب WooCommerce ارزیابی شوند. افزونهٔ اختصاصی فقط برای نیازهای واقعی و پوشش‌داده‌نشده ساخته شود.

### محصولات و Commerce
- WooCommerce باید گزینهٔ اصلی بررسی باشد؛ مدل محصول، قیمت، موجودی، دسته‌بندی، تصویر، وضعیت انتشار، URL و اکوسیستم افزونه‌ها را فراهم می‌کند.
- اگر WooCommerce نیازهای فعلی را پوشش می‌دهد، از product model و API آن استفاده کن؛ مدل موازی نساز مگر دلیل مشخصی وجود داشته باشد.
- اگر پنل اختصاصی برای UX یا جریان کاری لازم است، آن را به همان داده‌های WordPress/WooCommerce متصل کن تا دو منبع حقیقت ایجاد نشود.
- WordPress REST API و در صورت نیاز WooCommerce REST API با مجوزدهی مناسب استفاده شوند. کلیدهای محرمانه نباید در bundle مرورگر قرار بگیرند.
- فیلدهای محصول لازم برای SEO و فید پس از بررسی نیازهای فعلی و مشخصات ترب تعیین شوند.

### Frontend
- حفظ UI فعلی Next.js تا جای ممکن و تولید خروجی استاتیک قابل میزبانی.
- اتصال به API وردپرس از طریق HTTP؛ داده‌های عمومی محصولات می‌توانند عمومی/محدودشده باشند، عملیات مدیریتی و کاربر باید امن باشند.
- فارسی، RTL و تومان حفظ شوند.
- بررسی کن آیا فروشگاه استاتیک مستقل با checkout، سبد، قیمت/موجودی و SEO سازگار است یا قالب/فرانت‌اند WordPress/WooCommerce یا معماری ترکیبی ساده‌تر و قابل‌اتکاتر است. این trade-off باید مستند شود.

### WordPress و محتوا
- WordPress برای صفحات محتوایی، بلاگ و SEO استفاده شود.
- ترجیح کاربر بلاگ در /blog/ و فروشگاه روی دامنهٔ اصلی است.
- بررسی شود که قرار دادن WordPress در ریشه با فرانت‌اند استاتیک Next.js تداخل دارد یا با routing وب‌سرور قابل ترکیب است. اگر پیچیدگی غیرضروری ایجاد می‌کند، گزینهٔ جایگزین و trade-off را روشن پیشنهاد بده.
- منطق اختصاصی دامنه، در صورت نیاز، در افزونهٔ کوچک مستقل قرار گیرد نه در قالب.

### ترب و فید محصول
- ترب یک نیاز مشخص برنامهٔ فروشگاه است، نه صرفاً ایده‌ای برای آینده.
- قبل از پیاده‌سازی بررسی شود ترب اکنون چه روش‌هایی برای ثبت فروشگاه، خزش اطلاعات محصول، feed یا integration مورد تأییدی دارد.
- گزینه‌ها: integration معتبر WordPress/WooCommerce؛ سپس feed مطابق مشخصات رسمی ترب؛ سپس اتصال سفارشی فقط اگر لازم باشد.
- شناسهٔ پایدار محصول، نام/برند، قیمت نهایی، موجودی، URL محصول، تصویر، دسته‌بندی و زمان به‌روزرسانی فقط تا جایی در قرارداد داده لحاظ شوند که مستندات جاری ترب تأیید کنند.
- قیمت و موجودی باید صحیح و URL محصول پایدار و برای crawler قابل دسترس باشد. جزئیات الزامی را از منابع رسمی جاری تأیید کن؛ حدس را الزام اعلام نکن.
- اگر ترب به URL محصول عمومی و crawlable نیاز دارد، خروجی استاتیک باید صفحات محصول واقعی با URL پایدار بسازد؛ نمایش محصول فقط در یک صفحه یا modal ممکن است کافی نباشد. این موضوع باید در ممیزی routeها و معماری بررسی شود.

### تصاویر
- محل نگهداری تصاویر باید با WordPress Media Library/WooCommerce سازگار باشد، مگر اینکه ممیزی محدودیت دیگری نشان دهد.
- URL تصویر باید برای فرانت‌اند، SEO و feed قابل دسترس باشد.

## 6. راهبرد مهاجرت

1. ممیزی فقط‌خواندنی routeها، ناسازگاری‌های static export، وابستگی‌های Firebase، مدل داده، CRUD، auth، سبد/سفارش، آپلود و قابلیت‌های موجود.
2. بررسی WordPress/WooCommerce و ترب: قابلیت‌های بومی، افزونه‌های معتبر و مستندات فعلی ترب.
3. تثبیت معماری: تعیین اینکه WooCommerce هستهٔ product/order باشد یا WordPress ساده با افزونهٔ اختصاصی؛ تصمیم با نیاز واقعی و محدودیت هاست توجیه شود.
4. طراحی URL محصول و مسیرهای محتوا، بلاگ و API با درنظرگرفتن crawlability و feed.
5. آماده‌سازی static export با کمترین تغییر؛ اگر با checkout/SEO/ترب ناسازگار بود، گزینهٔ ساده‌تر با شواهد پیشنهاد شود.
6. پیاده‌سازی endpoint/افزونه‌های ضروری که قابلیت استاندارد پوشش نمی‌دهد.
7. انتقال خواندن محصولات و دسته‌ها.
8. انتقال CRUD مدیریت به همان دیتابیس WordPress/WooCommerce.
9. انتقال auth با بررسی قابلیت‌های بومی WordPress/WooCommerce.
10. backup، تطبیق داده‌ها و برنامهٔ بازگشت قبل از مهاجرت.
11. حذف Firebase فقط پس از تأیید انتقال کامل قابلیت‌ها.
12. بررسی مسیرهای استاتیک، /blog/، /wp-admin/ و API در هاست هدف.
13. پس از پایداری عملکرد، آزمایش feed/integration ترب و SEO محصول: metadata، structured data، sitemap، canonical و crawlability.

از dual-write به‌عنوان پیش‌فرض استفاده نکن؛ منبع داده و ترتیب cutover شفاف باشد.

## 7. معیارهای پذیرش مرحلهٔ اول

- فروشگاه با روش سازگار با هاست بدون Node.js اجرا شود.
- WordPress (و در صورت انتخاب WooCommerce) منبع واحد اطلاعات محصولات باشد.
- Firebase پس از مهاجرت دیگر وابستگی runtime حیاتی نباشد.
- عملیات مدیریت محصول در دیتابیس WordPress/WooCommerce ثبت شود.
- ثبت‌نام/ورود بدون Firebase کار کند و مجوز مدیریت سمت سرور باشد.
- قیمت و موجودی پیش از عملیات حساس سمت سرور اعتبارسنجی شوند.
- URL محصول، تصویر و اطلاعات لازم برای SEO و ترب قابل اتکا باشند؛ مشخصات feed از مستندات جاری ترب تأیید شوند.
- مسیرهای API، بلاگ و فایل‌های استاتیک تداخل نداشته باشند.
- lint، format/syntax، تست‌ها و build بررسی شوند و موارد غیرقابل تست صریحاً گزارش شوند.
- مستند معماری پس از تغییر با وضعیت واقعی همگام شود.

## 8. پرسش‌های باز

ابتدا با کد، مستندات معتبر و امکانات هاست پاسخ‌های ممکن را پیدا کن؛ سپس فقط سؤال‌های تصمیم‌ساز را بپرس.

### استقرار
- آیا WordPress نصب شده؟
- آیا تنظیمات Apache/.htaccess یا Nginx قابل تغییرند؟
- فرانت‌اند و WordPress در یک document root قرار می‌گیرند؟ URL پایهٔ API چیست؟
- آیا HTTPS روی دامنه و API فعال است؟

### Commerce و WordPress
- آیا WooCommerce نصب یا استفاده می‌شود؟ اگر نه، دلیل یا محدودیتی برای آن وجود دارد؟
- چه قابلیت‌هایی از سفارش، checkout، پرداخت، ارسال، کد تخفیف و انبار در نسخهٔ فعلی وجود دارد و باید حفظ شود؟ ابتدا repo را بررسی کن.
- پنل مدیریت اختصاصی باید حتماً حفظ شود یا می‌توان بخشی از مدیریت را به پنل بومی منتقل کرد؟
- ساختار واقعی محصول چیست؟ (SKU، قیمت عادی/تخفیف، قیمت همکاری، حداقل خرید عمده، ویژگی‌ها، موجودی، انتشار، تصاویر، دسته‌بندی و slug.)
- آیا داده‌های محصولات/کاربران باید از Firebase export شوند؟
- تصاویر کجا نگهداری شوند؟

### ترب و SEO
- آیا فروشگاه در ترب از قبل ثبت شده یا ثبت‌نام باید از ابتدا انجام شود؟
- آیا دامنه و صفحات محصول عمومی آماده‌اند؟
- الزامات فعلی ترب برای ثبت فروشگاه و feed باید از مستندات جاری تأیید شوند.
- URL مستقل و crawlable محصول باید از ابتدا در طراحی لحاظ شود.

### عملیات
- آیا امکان build محلی/CI و بارگذاری خروجی استاتیک وجود دارد؟
- روش backup دیتابیس و محیط تست API چیست؟

## 9. قدم بعدی دقیق

**بدون تغییر کد، ممیزی فقط‌خواندنی انجام بده و گزارش را بر اساس شواهد مخزن و مستندات معتبر آماده کن.**

گزارش شامل:
1. routeها و موارد ناسازگار با static export.
2. تمام محل‌های Firebase و قابلیت‌های وابسته.
3. جریان CRUD محصولات/دسته‌ها/تنظیمات، کاربران و قابلیت‌های سفارش/پرداخت موجود.
4. ارزیابی تطبیق قابلیت‌ها با WordPress/WooCommerce؛ چه چیزی استاندارد است و چه چیزی واقعاً نیاز به توسعهٔ اختصاصی دارد.
5. بررسی مستندات جاری ترب و روش‌های مورد تأیید برای معرفی محصول.
6. پیشنهاد معماری حداقلی سازگار با هاست که صفحات محصول crawlable، دادهٔ یکپارچه و ترب را پشتیبانی کند.
7. سؤال‌های باقی‌ماندهٔ لازم برای تصمیم معماری.

در این مرحله مجاز به حذف Firebase، تغییر پیکربندی build یا شروع بازنویسی نیستی؛ ابتدا گزارش و ابهام‌های مهم را ارائه کن. پس از تأیید جهت کار، پیاده‌سازی مرحله‌ای آغاز شود.

## 12. نتیجهٔ ممیزی اولیه (2026-10-17)

این بررسی فقط‌خواندنی است؛ کد برنامه و تنظیمات استقرار تغییر نکرده‌اند.

### UI و مسیرها
- صفحهٔ اصلی فعلی `app/page.tsx` است و از کامپوننت‌های اختصاصی React در `components/store/` استفاده می‌کند. تصمیم کاربر این است که UI/UX با کدنویسی اختصاصی توسعه یابد؛ Elementor/page builder مبنای طراحی نیست.
- مسیرهای اپ فعلی شامل `/` و `/admin/` هستند؛ مسیر مستقل محصول/دسته/checkout در پوشهٔ `app/` مشاهده نشد.
- `next.config.ts` فقط با `GITHUB_PAGES=true` خروجی export می‌سازد؛ حالت پیش‌فرض `standalone` است و `headers()` نیز در حالت غیر export تعریف شده است. مستندات رسمی Next.js می‌گوید static export از قابلیت‌هایی مانند headers و runtimeهای وابسته به درخواست پشتیبانی نمی‌کند. بنابراین export واقعی هنوز اثبات نشده و باید با build بررسی شود.
- `images.unoptimized: true` تنظیم شده، اما این به‌تنهایی سازگاری کل پروژه با export را ثابت نمی‌کند.
- مرجع: https://nextjs.org/docs/app/guides/static-exports

### Firebase و قابلیت‌های فروشگاه
- `lib/firebase.ts` و hookهای `hooks/useStoreProducts.ts` و `hooks/useStoreAuth.ts` به Firebase/Firestore متصل‌اند.
- `useStoreProducts` محصولات، دسته‌ها و `store_settings` را می‌خواند/مدیریت می‌کند.
- `useStoreAuth` کاربران را از `users_directory` می‌خواند و نشست را در localStorage نگه می‌دارد. مدل کاربر فعلی فیلد رمز عبور قابل‌بازیابی دارد؛ این طراحی برای فروشگاه واقعی امن نیست و باید در مهاجرت با احراز هویت بومی WordPress و کنترل دسترسی سمت سرور جایگزین شود.
- سبد خرید در localStorage است. `components/CartDrawer.tsx` هنگام checkout صرفاً state محلی موفقیت را تغییر می‌دهد؛ در مسیرهای بررسی‌شده ثبت سفارش یا پرداخت واقعی سمت سرور دیده نشد.
- مدل محصول فعلی شامل عنوان، دسته، قیمت اصلی/تخفیف، قیمت عمده و حداقل تعداد، تصاویر، ویژگی‌ها، موجودی و گارانتی است. هنگام مهاجرت باید این فیلدها به WooCommerce نگاشت شوند و فقط داده‌های اختصاصی ضروری به metadata تبدیل شوند.

### معماری موقت و قدم بعدی
1. WordPress/WooCommerce منبع اصلی محصولات، موجودی و سفارش‌ها باشد.
